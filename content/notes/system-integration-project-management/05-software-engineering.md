# 软件工程

## 考情分析
- 本章是软件工程核心章节，分值占比约5～8分
- 常见题型：选择题 + 简答题（需求、测试、设计模式）
- **高频考点**：需求层次、结构化设计（耦合与内聚）、面向对象设计原则、UML图、软件测试方法、CSM成熟度等级

## 核心考点

### 一、软件需求（5.2）

**需求三个层次**：
- **业务需求**：组织的高层次目标
- **用户需求**：用户的任务和目标
- **系统需求**：系统的功能、性能等具体要求

**需求分析方法**：
- **结构化分析（SA）**：数据流图（DFD）+ 数据字典（DD）。DFD包含四种基本符号——外部实体、过程、数据存储、数据流。
- **面向对象分析（OOA）**：包括5个层次（主题层、对象类层、结构层、属性层、服务层）和5个活动（标识对象类、标识结构、定义主题、定义属性、定义服务）。

**OOA基本原则**：抽象、封装、继承、分类、聚合、关联、消息通信、粒度控制、行为分析。

**需求规格说明书（SRS）**：需求分析的最终结果文档，包含范围、引用文件、需求、合格性规定、需求可追踪性、尚未解决的问题、注解和附录。需通过**需求评审**和**需求测试**进行验证。

**需求变更控制过程**：识别问题 → 问题分析和变更描述 → 变更分析和成本计算 → 变更实现 → 修改后的需求。

**变更控制委员会（CCB）**：项目所有者权益代表，负责裁定接受哪些变更。是决策机构不是作业机构。

**需求跟踪**：正向跟踪（SRS每个需求 → 后继工作成果）+ 逆向跟踪（工作成果 → SRS出处）= 双向跟踪。

### 二、软件设计（5.3）

#### （1）结构化设计（SD）

**核心思想**：自顶向下、逐层分解、逐步求精、模块化。

**模块的耦合类型**（从低到高）：

| 耦合类型 | 描述 |
|------|------|
| **非直接耦合** | 无直接关系，通过上级模块调用 |
| **数据耦合** | 通过参数表传递简单数据 |
| **标记耦合** | 通过参数表传递复杂数据结构 |
| **控制耦合** | 传递控制模块内部逻辑的信息 |
| **通信耦合** | 共享输入或输出 |
| **公共耦合** | 访问同一公共数据环境 |
| **内容耦合** | 直接访问另一模块内部数据 |

**模块的内聚类型**（从高到低）：
功能内聚 > 顺序内聚 > 通信内聚 > 过程内聚 > 时间内聚 > 逻辑内聚 > 偶然内聚。

设计原则：**高内聚、低耦合**。

#### （2）面向对象设计（OOD）

**常用OOD原则**：

| 原则 | 核心 |
|------|------|
| **单一职责原则** | 一个类仅有一个引起变化的原因 |
| **开闭原则** | 对扩展开放，对修改封闭 |
| **里氏替换原则** | 子类可替换父类 |
| **依赖倒置原则** | 依赖于抽象而非具体实现 |
| **接口隔离原则** | 多个专门接口优于单一总接口 |
| **组合重用原则** | 尽量使用组合而非继承 |
| **迪米特原则** | 对象对其他对象尽可能少了解 |

**OOD中类的三种类型**：
- **实体类**：保存需要永久存储的信息，有属性但不一定有方法
- **控制类**：控制用例工作，有方法但通常无属性
- **边界类**：封装内外信息流动，位于系统与外界交接处

#### （3）UML（统一建模语言）

**UML结构**：构造块（事物、关系、图）+ 规则 + 公共机制。

**UML四种事物**：结构事物、行为事物（交互/状态机）、分组事物（包）、注释事物。

**UML四种关系**：依赖、关联、泛化、实现。

**UML 2.0包括14种图**，常用：类图、对象图、用例图、顺序图、通信图、状态图、活动图、部署图、构件图。

**UML五个系统视图**：逻辑视图、进程视图、实现视图、部署视图、用例视图。

#### （4）设计模式

按目的分三类：
- **创建型**：工厂方法、抽象工厂、单例、原型、建造者
- **结构型**：适配器、桥接、组合、装饰、外观、享元、代理
- **行为型**：观察者、策略、模板方法、命令、状态、职责链等

### 三、软件测试（5.4.3）

**测试方法**：
- **静态测试**：不运行程序，依靠分析检查。包括桌前检查、代码走查、代码审查。可发现30%～70%逻辑错误。
- **动态测试**：
  - **白盒测试**（结构测试）：了解内部结构，测试逻辑覆盖。标准包括语句覆盖、判定覆盖、条件覆盖、路径覆盖等。
  - **黑盒测试**（功能测试）：不了解内部结构，按需求测试功能。方法包括等价类划分、边界值分析、判定表等。

**测试类型**：

| 类型 | 说明 |
|------|------|
| **单元测试** | 对模块进行测试，技术依据是详细设计说明书 |
| **集成测试** | 对组装后的模块进行测试，技术依据是概要设计文档 |
| **确认测试** | 验证软件功能性能是否与用户需求一致 |
| **系统测试** | 真实环境下的完整系统测试，含功能、性能、健壮性等 |
| **配置项测试** | 检验软件配置项与SRS的一致性 |
| **回归测试** | 变更后验证正确性和无害性 |

### 四、部署交付（5.5）

**持续交付**：确保代码能够快速、安全地部署到生产环境中。

**容器技术优点**：轻量级、体积小、集合性好、容易打包复制发布。

**部署原则**：统一存储库、相同部署方式与脚本、阶梯式晋级、不可变服务器等。

**两大部署方式**：
- **蓝绿部署**：新旧两个版本并行，通过域名切换，出问题可快速回退
- **金丝雀部署**：先少量用户试用新版本，逐步扩大到所有用户

### 五、软件过程能力成熟度（CSM）（5.7）

CSM模型由4个能力域、20个能力子域、161个能力要求组成。

**4个能力域**：治理、开发与交付、管理与支持、组织管理。

**五个成熟度等级**：

| 等级 | 名称 | 特征 |
|------|------|------|
| 1级 | **初始级** | 过程和结果不确定，依赖个人能力 |
| 2级 | **项目规范级** | 项目按规范执行，基本实现预期结果 |
| 3级 | **组织改进级** | 组织范围内稳定实现目标，持续改进 |
| 4级 | **量化提升级** | 使用统计分析技术量化管理 |
| 5级 | **创新引领级** | 技术和管理的创新，引领行业发展 |

## 记忆要点
- **需求三层次**：业务需求→用户需求→系统需求
- **耦合度口诀**（低到高）：非数标控通公内
- **内聚度口诀**（高到低）：功顺通过时逻偶
- **OOD七原则**：单开里依接口组迪
- **UML四种关系**：依赖、关联、泛化、实现
- **测试类型记忆**：单集确系配回（单元→集成→确认→系统→配置项→回归）
- **设计模式三类**：创建型（建对象）、结构型（组对象）、行为型（对象交互）
- **CSM五级**：初始→规范→改进→量化→创新

## 常见题型
1. **选择题**：软件需求的常用层次（不含"数据需求"）
2. **选择题**：不属于SRS内容的是（算法的详细过程）
3. **选择题**：关于需求变更策略不正确的是（应由CCB而非项目经理决定变更）
4. **选择题**：CSM分为几个等级（5级）
5. **选择题**：蓝绿部署的描述（准备新旧两版本，通过域名切换）
6. **简答题**：软件测试方法都有哪些（静态测试、动态测试；白盒测试、黑盒测试）
