# 组织保障

## 考情分析
- 本章涵盖**信息和文档管理**、**配置管理**、**变更管理**三大主题
- 选择题高频考点：文档分类（开发/产品/管理）、文档质量分级、配置项状态与版本号、配置库类型、CCB职责、变更管理原则与流程
- 简答题高频考点：配置管理活动、变更管理流程（8步）、变更分类、基于配置库的变更控制
- 预计分值：选择题3~5分，简答题偶尔涉及

## 核心考点

### 15.1 信息和文档管理

#### 15.1.1 信息和文档
**信息系统信息的分类：**
1. **用户信息**：个人或组织的基本信息、账号信息、信用信息、行为数据
2. **业务信息**：按行业划分（金融、能源、交通等）；按业务特点细分（研发、生产、维护等）
3. **经营管理信息**：市场营销、经营、财务、并购或融资、产品、运营或交付信息
4. **系统运行信息**：系统配置信息、监测数据、备份数据、日志数据、安全漏洞信息

**信息系统文档分类（开发项目）：**
- **开发文档**（描述开发过程）：可行性研究报告和项目任务书、需求规格说明、功能规格说明、设计规格说明、开发计划、软件集成和测试计划、质量保证计划、安全和测试信息
- **产品文档**（描述开发过程的产物）：培训手册、参考手册和用户指南、软件支持手册、产品手册和广告
- **管理文档**（记录项目管理信息）：进度和进度变更记录、软件变更情况记录、开发团队职责定义、项目计划和阶段报告、配置管理计划

**文档质量4个等级：**
1. **1级（最低限度文档）**：开发工作量低于一个人·月的自用程序。含程序清单、开发记录、测试数据、程序简介
2. **2级（内部文档）**：没有与其他用户共享资源的专用程序。除1级外还需程序清单内足够的注释
3. **3级（工作文档）**：同一单位内若干人联合开发或被其他单位使用的程序
4. **4级（正式文档）**：正式发行供普遍使用的软件产品。遵守GB/T8567《计算机软件文档编制规范》

#### 15.1.2 信息（文档）管理规则和方法

**文档规范化管理四方面：**
1. **文档书写规范**：文本、图形、表格遵循统一规范，包括符号使用、图标含义、注释行使用、注明书写人及日期
2. **图表编号规则**：一般按分类结构编号（生命周期法5个阶段），通过编号可判断图表出自哪个阶段
3. **文档目录编写标准**：含文档编号、文档名称、格式或载体、份数、页数、存储地点、存档时间、保管人
4. **文档管理制度**：建立文档规范、文档借阅登记制度、文档使用权限控制规则

**文档定级保护：**
- 影响对象：个人/法人合法权益；社会秩序/公共利益；国家安全
- 侵害程度：无影响→一般损害→严重损害→特别严重损害
- 文档中有密级要求的，应保密和权限管理；签字确认后的文档与电子文档一对一对应，电子文档设置为只读

### 15.2 配置管理

#### 15.2.1 基本概念
- **配置管理定义**：应用技术的和管理的指导和监控方法以标识和说明配置项的功能和物理特征，控制这些特征的变更，记录和报告变更处理和实现状态并验证与规定需求的遵循性（GB/T 11457）

**1. 配置项（CI）：**
- 为配置管理设计的硬件、软件或两者的集合，在配置管理过程中作为单个实体对待
- 典型CI：项目计划书、技术解决方案、需求文档、设计文档、源代码、可执行代码、测试用例、运行软件所需数据、设备型号及关键部件
- **基线配置项**：所有设计文档和源程序等（向开发人员开放读取权限）
- **非基线配置项**：各类计划和报告等（向项目经理、CCB及相关人员开放）

**2. 配置项状态：**
- **草稿**→通过评审→**正式**→变更控制→**修改**→再次通过评审→正式
- 三种状态：草稿、正式、修改

**3. 配置项版本号：**
- **草稿状态**：0.YZ（YZ范围01~99）
- **正式状态**：X.Y（X为主版本号1~9，Y为次版本号0~9）。第一次成为正式时版本号为1.0
- **修改状态**：X.YZ。修改完成状态变为正式时Z值设为0，增加X.Y值
- 升级幅度小：制作附件（1.0, 1.1...）；升级幅度大：直接增大X值

**4. 配置基线：**
- 由一组配置项组成，构成相对稳定的逻辑实体
- 基线中的配置项被"冻结"，不能再被任何人随意修改
- 对基线的变更必须遵循正式的变更控制程序
- 基线通常对应项目过程中的**里程碑**
- **发行基线（Release）**：交付给用户使用的基线
- **构造基线（Build）**：内部过程使用的基线
- 建立基线的价值：提供定点和快照；新项目可在基线上建立；提供取消变更的方法；可重建特定发布版本

**5. 配置库三种类型（必考！）：**
- **开发库（动态库/程序员库/工作库）**：保存开发人员当前正在开发的配置实体。由开发人员自行控制，无须配置控制
- **受控库（主库）**：包含当前基线加上对基线的变更。被置于完全的配置管理之下。阶段工作结束时将工作产品存入
- **产品库（静态库/发行库/软件仓库）**：包含已发布使用的各种基线的存档。系统测试之后作为最终产品存入，等待交付用户

**配置库建库模式：**
- **按配置项类型建库**：适用于通用软件开发组织（产品继承性强，工具统一，并行开发需求）
- **按开发任务建库**：适用于专业软件开发组织（工具种类多，线性发展为主）

#### 15.2.2 角色与职责
- **CCB（配置控制委员会/变更控制委员会）**：制定修改配置管理策略；审批发布配置管理计划；审批基线的设置和产品版本；审查、评价、批准、推迟或否决变更申请；监督已批准变更的实施；确认变更是否按要求完成
- **配置管理负责人（配置经理）**：管理所有配置活动；负责配置管理过程；审批配置库的结构性变更；定义配置项责任人；指派配置审计员
- **配置管理员**：建立和维护配置管理系统/配置库/CMDB；配置项识别；建立和管理基线；版本管理和配置控制；配置状态报告；配置审计；发布管理和交付
- **配置项负责人**：记录所负责配置项的所有变更；维护配置项间关系；调查审计中发现的差异；遵从配置管理过程

#### 15.2.4 管理活动（6项）
1. **制订配置管理计划**：CCB审批。内容包括目标和范围、活动、角色责任、规范流程、进度、接口控制、信息系统规划、日常事务、基线里程碑和资源计划
2. **配置项识别**：识别需要受控的配置项→分配唯一标识号→定义重要特征→确定所有者和责任→确定进入配置管理的时间和条件→建立和控制基线→维护文档和组件修订与产品版本间关系
3. **配置项控制（变更控制）**：变更申请→变更评估（CCB评估影响、必要性、范围、方案可行性、工作量）→通告评估结果→变更实施→变更验证与确认→变更的发布→**基于配置库的变更控制**（检出Check out→锁定→修改→检入Check in→解除锁定）
4. **配置状态报告**：记录和报告每个受控配置项的标识和状态；每个变更申请的状态；每个基线的当前和过去版本状态
5. **配置审计**：
   - **功能配置审计**：验证配置项的一致性（实际功效是否与需求一致）——开发已完成、达到规定性能和功能特征、操作和支持文档已完成
   - **物理配置审计**：验证配置项的完整性（物理存在是否与预期一致）——要交付的配置项是否存在、是否包含了所有必需项目
   - 审计场景：实施新配置库后；重大变更前后；发布安装前；灾难恢复后；发现未授权配置项后等
6. **配置管理回顾与改进**：定期回顾配置管理活动，找到改进点，优化配置管理过程

### 15.3 变更管理

#### 15.3.1 基本概念
- **项目变更**：由于项目环境或其他原因而对项目功能、性能、架构、技术指标、集成方法和项目进度等方面做出的改变
- **变更管理的实质**：根据项目推进过程中越来越丰富的项目认知，不断调整项目努力方向和资源配置，最大程度地满足项目需求，提升项目价值

**变更常见原因（6项）：**
1. 产品范围（成果）定义的过失或疏忽
2. 项目范围（工作）定义的过失或疏忽
3. **增值变更**
4. 应对风险的紧急计划或回避计划
5. 项目执行过程与基准要求不一致带来的被动调整
6. 外部事件

**变更分类：**
- 按性质：**重大变更、重要变更、一般变更**（不同审批权限）
- 按迫切性：紧急变更、非紧急变更
- 按行业特征：产品范围变更、环境变更、设计变更、实施变更、技术标准变更

**变更管理7项原则：**
1. **基准管理**：基准是变更的依据，每次变更通过评审后重新确定基准
2. **变更控制流程化**：所有变更必须遵循控制流程
3. **明确组织分工**：明确评估、评审、执行的职能
4. **与干系人充分沟通**：征求重要干系人意见
5. **变更的及时性**：变更宜早不宜晚，只做必须要变更的
6. **评估变更的可能影响**：包括客户可视的成果变更和不可视的内部工作变更
7. **妥善保存变更产生的相关文档**：完整、及时、准确、清晰

#### 15.3.2 角色与职责
- **CCB（变更控制委员会）**：决策机构，不是作业机构。审查、评价、批准、推迟或否决项目变更；通知决定；确认变更是否按要求完成
- **变更管理负责人（变更经理）**：负责整个变更过程方案；监控变更管理过程；协调资源；确定变更类型；管理日程安排；实施完成后的回顾和关闭
- **变更请求者**：提出变更需求；记录并提交变更请求单；初步评价变更风险和影响
- **变更实施者**：按批准计划实施变更；记录和保存变更产物；参与变更验证与确认
- **变更顾问委员会**：紧急变更时可对被授权者行使审批权限；定期评估变更管理执行情况

#### 15.3.3 工作程序（8步流程，必背！）
1. **变更申请**：及时以正式方式提出，留下书面记录。项目干系人都可提出，一般由项目经理或配置管理员初审
2. **对变更的初审**：确认变更的必要性和价值；格式校验、完整性校验；在干系人间就评估信息达成共识
3. **变更方案论证**：对变更请求是否可实现进行论证；将技术要求转化为资源需求；包括技术评估和经济与社会效益评估
4. **变更审查**：项目所有者根据变更申请及评估方案决定是否变更项目基准。将专业评审、经济评审分开
5. **发出通知并实施**：基准调整包括项目目标确认、最终成果、工作内容和资源、进度计划的调整
6. **实施监控**：项目经理负责基准监控；CCB监控主要成果和进度里程碑；确认变更是否正确完成
7. **效果评估**：依据项目基准；检查变更目的是否达成；评估技术论证、经济论证与实施过程的差距
8. **变更收尾**：判断变更后项目是否已纳入正常轨道；确认资源配置是否及时到位

#### 15.3.4 变更控制
- **变更申请的控制**：严格控制变更申请提交；确保变更管理体系能确保项目基准反映项目实施情况
- **进度变更控制**：判断当前进度状态；对造成进度变化的因素施加影响；查明进度是否已改变
- **成本变更控制**：对造成费用基准变更的因素施加影响；确保变更请求获得同意；保证潜在费用超支不超过授权范围
- **合同变更控制**：与整体变更控制结合起来

**变更类型控制：**
- **标准变更**：低风险、预先授权，已充分理解和完整记录，不需要额外授权
- **正常变更**：常规、较低风险，通过确定的变更授权角色和流程管理
- **紧急变更**：必须快速响应（如业务中断、安全攻击），程序可精简

#### 15.3.5 版本发布和回退计划
**版本发布前准备工作：**
- 进行回退分析
- 备份存储过程、函数等数据
- 备份配置数据
- 备份在线生产平台接口、应用和工作流版本
- 明确启动回退机制的触发条件
- 对变更回退机制职责的说明

**回退步骤（8步）：**
1. 通知相关用户系统开始回退
2. 通知各关联系统进行版本回退
3. 回退存储过程等数据对象
4. 配置数据回退
5. 应用程序、接口程序、工作流等版本回退
6. 回退完成通知各周边关联系统
7. 回退后进行相关测试
8. 通知用户回退完成

## 记忆要点
1. **文档三种类型**：开发文档（过程）、产品文档（产物）、管理文档（项目管理）
2. **文档四级质量**：1级最低限度→2级内部→3级工作→4级正式
3. **配置项三种状态**：草稿→正式→修改（循环）
4. **配置库三种类型**：开发库（动态/自由）→受控库（主库/受控）→产品库（静态/存档）
5. **配置管理6项活动**：计划→识别→控制→状态报告→审计→回顾改进
6. **变更管理8步流程**：申请→初审→方案论证→审查→通知并实施→实施监控→效果评估→收尾
7. **CCB是决策机构，不是作业机构**
8. **变更7项原则**口诀：基准流程化，分工沟通早，评估存文档

## 常见题型
1. **选择题**：项目变更管理的实质是？
   - 答：A. 不断调整项目努力方向和资源配置，提升项目价值
2. **选择题**：项目变更的依据是？
   - 答：C. 项目基准
3. **选择题**：变更管理首要完成的任务是？
   - 答：A. 分析变更的必要性和合理性，确认是否实施变更
4. **选择题**：关于变更流程的做法中，错误的是？
   - 答：C. 为了规范，监理不对变更进行分级，所有变更流程都不能简化
5. **选择题**：软件版本发布前的准备工作一般不包括？
   - 答：C. 系统应急方案
6. **简答题**：简述配置管理的日常管理活动。
   - 答：制订配置管理计划、配置项识别、配置项控制、配置状态报告、配置审计、配置管理回顾与改进
